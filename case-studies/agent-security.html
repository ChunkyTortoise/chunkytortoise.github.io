Work / Agent security

Prompt scaffolding doesn't fix a broken tool-call substrate. Typed dispatch does.

Pre-registered research on indirect prompt injection through agent tool output, with the misses published alongside the hits.

Codemake repro

Problem

Agents read tool output: web pages, files, API responses. If an attacker controls that output, can they make the agent leak data? The common answer is to add a defensive prompt telling the model to distrust tool content. I wanted to know whether that holds up, and whether a bigger model is safer.

Approach

  • Pre-registered hypotheses. Each experiment's hypotheses and success criteria were written down and dated before the runs, with Wilson 95% confidence intervals at n=10 (ledger).
  • Controlled substrate. The same payloads ran through an inline text/XML tool-dispatch substrate and a chat-only control, so the dispatch mechanism could be isolated from the model.
  • Safe targets only. Intentionally vulnerable benchmarks, open-weight models via public APIs and localhost harnesses. Nothing in production was tested without authorization.
  • A tool, not just a writeup. The finding became substrate_auditor.py, a zero-dependency check that flags risky dispatch substrates and runs in CI.

Architecture

Results

Strict canary exfiltration on Llama-3.3-70B through the inline-XML dispatch substrate:

ConditionExfiltratedWhat it shows
Content-trust scaffold (M1), payload v710 / 10The scaffold failed completely against this variant
Content-trust scaffold (M1), payload v30 / 10The same scaffold stopped a different variant
Chat-only control (no XML dispatch)0 / 10The dispatch substrate, not the model alone, is the exposure

Takeaway: prompt scaffolding is variant-selective. It blocked some payloads and not others, so it can't be the fix on its own. The durable fix belongs in the agent client: typed tool-call dispatch, with authorization and provenance checks outside the model, and prompt hardening as defense in depth. Source: the H10b-G report.

Published misses. The pre-registered assumption that a larger model would be safer here (H7) was falsified at 70B. H3 was retracted for a substrate confound, H6 and H11 were falsified, and one mitigation (M2) measured as a regression. They're listed in the hypothesis ledger because a record that hides its nulls is harder to trust.

What I'd do next

  • Replicate the 70B grid on a second inference provider; the current grid is single-provider.
  • Extend the payload set and the auditor's checks to more agent frameworks' dispatch formats.
  • Package substrate_auditor as a pre-deploy check other teams can drop into CI.

Methodology & limits

Scope of the evidence
  • "Typed dispatch is the fix" is architectural reasoning backed by thin measurement: the typed-substrate cell is a single simulated 8B run. At 70B, the isolation check is the chat-only control, not a typed substrate.
  • The H10b-G grid used n=10 per cell on a single hosted provider. An earlier 8B baseline was n=5 on a free tier and is directional only.
  • Targets were intentionally vulnerable benchmarks, open-weight models and local harnesses, under a three-tier disclosure policy enforced by a pre-push hook.
  • Full claim-to-run mapping and limitations: the repository README and research summary.
