Eval-driven multi-model runs: contracts, gates, and a kill

I run Claude Code, Codex, and Cursor on the same machine. The failure mode is not "the model wrote bad code." It is two writers on one branch, a stale pane that still thinks it owns the change, and a claim nobody can rerun. This note is how I coordinate those runtimes. It is personal developer infrastructure, not a product, and it is not the proof that I ship systems. That proof is still DocExtract, the Acuity engagement, and mcp-server-toolkit.

The problem

Three coding-agent surfaces, used in parallel, create three cheap ways to lie to yourself:

  • Two panes edit the same files. Git looks busy. Ownership is gone.
  • A session outlives the task. The next agent resumes stale context and "fixes" work that already moved.
  • A model summarizes its own run as evidence. The summary is not a command you can replay.

I wanted a pattern a hiring engineer can audit in one sitting: who may write, who may only check, what artifact counts as a result, and what happens when the check loses. Automation can observe, stamp, and refuse a second writer. It cannot accept the change. That last step stays human.

The pattern

Work is scoped to a mission, not to a model. A model is a lane for a stage. The standing rule is one writer per resource boundary, plus an independent gate from a different model family. The human accepts. I use cmux as the pane and fanout surface for that contract.

  • Conduct plans and reports. It does not write the shared artifact, merge, or declare done.
  • Build is the only writer for the declared branch, worktree, or file set.
  • Gate reruns named checks from the diff. It does not read the builder's rationale.
  • Result contract is a nonce-stamped result file. A result without the nonce is not a result.

The handoff a receiver gets is mechanical, not a chat paste: what changed, which commands were run, the exit codes, and one claim they can rerun in a single command. Models may summarize those fields. They may not author them. If the nonce is missing, or a second writer targets the same resource, the run is refused rather than "merged in conversation."

That is employer language for orchestration with an eval gate, not a multi-user control plane. There is no SaaS, no daemon customers log into, and no second tenant.

What was measured

The interesting result is a reject.

On 2026-08-06 I compared two ways to draft a research digest, N=5 fixed cases. Baseline: Opus one-shot. Candidate: an advice-profile fanout on Sonnet. Promote required schema 5/5 and a blind preference of at least 3/5 versus baseline.

Opus one-shot won 4 of 5 blind preferences. Mean wall clock was 48s for the candidate and 47s for the baseline: not a latency win. Both promote gates missed, so the play was rejected. Routing did not change. That is the point. A coordination layer that loses to a strong one-shot on the task it was supposed to improve does not get a pin on GitHub.

A separate three-change documentation pilot (2026-08-07) did meet its scored accept-clock bar: each accepted change landed under 1.5 times a 307-second baseline (0.38x, 0.61x, 0.09x). That is process timing, not model quality, and it is not a cost or token claim. I do not have a production unit-economics study for this workflow yet, so this page does not invent one.

What this is not

  • Not a public hero repository. The executable orchestrator stays private. The research hub stays private. Publishing either would ship history, local paths, and unfinished lanes.
  • Not Phase 2. Codex, Gemini, and Grok interop rows are still blocked. This page does not claim those lanes run.
  • Not an agent OS, control plane, or enterprise platform. Operational prototype. One operator.
  • Not a substitute for shipped systems. If you are hiring for production LLM work, start with DocExtract, Acuity, and mcp-server-toolkit.

How to read this if you are hiring

Read it as judgment under measurement. I built a contract for multi-runtime work, ran a comparison, and killed the play that lost. I did not rebrand the loss as a platform.

A February 2026 post on this site covers cross-bot handoffs inside EnterpriseHub (Lead, Buyer, Seller). That is product orchestration for a CRM mesh. This page is the developer-runtime contract. Do not treat them as the same artifact.

If you want code you can clone, open the flagship repos. If you want to know how I keep two models from stepping on the same files, and what I do when a fancier routing loses the eval, this is the note.
